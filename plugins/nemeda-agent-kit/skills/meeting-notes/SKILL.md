# Meeting notes

The kit files every transcribed recording as `<meetings.transcripts>/<date>-<slug>/`
with `transcript.txt`, `transcript.srt`, `transcript.json`, and `meta.json`, and
normally writes the notes itself right after transcribing. This skill is the
manual path for the same result.

1. Locate the transcript folder: the user names it, or run
   `nemeda-agent meeting list` and pick from "Transcribed". Read `meta.json`
   (title, date, engine, recording) and `transcript.txt`.
2. Prefer the kit's own generator, which uses the same template and logs the
   memory entry: `nemeda-agent meeting notes <folder>` (add `--force` to
   regenerate). It reports `manual` when no local `claude` or `codex` CLI is
   available; only then write the notes yourself, in step 3.
3. Writing them yourself: use the same language as the transcript and exactly
   four sections with translated headings — Summary (five to eight sentences),
   Decisions (one bullet each, or "none"), Action items (owner, action, due date
   when said; "unassigned" when unclear), Open questions. Never invent names,
   numbers, or dates that are not in the transcript. Start the file with the
   header the generator uses: title and date, then a list with Date, Recording,
   Transcript path, and "Generated by: <you>". Save it as
   `<meetings.notes>/<date>-<slug>.md`; never overwrite an existing file unless
   the user asks.
4. Log the meeting: `nemeda-agent memory add --type meeting --title "<title> (<date>)"`
   with the Summary section on stdin, when the workspace has a `memory`
   section. Skip silently when it does not.
5. Tell the user where the notes are, list the action items with owners, and
   point out anything the transcript left ambiguous (unclear owners, missing
   dates) rather than guessing.

Notes and memory entries are project artifacts on the shared drive; keep them
free of secrets and of anything the transcript does not support.
